# Programming activity workbench

Updated 24 October 2026, Asia/Manila.

## Implementation status

The editor, real live diagnostics, private drafts, teacher settings/test cases, source snapshots and review integration are implemented. **Real Java, JavaScript, Python and Dart execution is now enabled for both roles through the managed OnlineCompiler sandbox.** The existing Judge0 adapter has a provider profile for its compatible API. No student program is executed on the TrueSight application host, and no output is generated by AI or simulated in the product.

The original static-only fallback was used until the user supplied `ONLINE_COMPILER_API_KEY`. The managed service has now passed 21 authored runtime checks, 37 end-to-end HTTP responses with execution assertions, and 18 availability checks against the running application on port 5000. The key and local evidence/approval file are ignored by Git. Provider architecture is documented and attested by the provider; it has not been independently audited by Codex.

## Existing architecture and issues corrected

- TrueSight already used `@uiw/react-codemirror` / CodeMirror 6, with built-in line numbers, indentation, bracket closing, folding, history and search. That editor is extended rather than replaced. Dart previously used the C++ language extension; it now has a Dart tokenizer, indentation and brace folding.
- Activities already stored `programming_language` and `starter_code`. Source was stored in the existing `submissions.content_text` and `submission_history`. These remain the official submission records. Existing language labels such as **Python** are preserved; canonical language identifiers are used internally for validation.
- The previous Judge0 endpoint accepted any authenticated caller's requested language without a class/activity scope. It also reran JavaScript/Python programs to display a final expression when the original program produced no output. The unscoped endpoint now returns 410, and the expression-capture rerun was removed. A run sends the original source once, and empty stdout remains empty.
- The old editor had no inline native diagnostics, server draft persistence, revision conflict protection, Problems panel or teacher test cases. These are additive changes inside the existing submission and class activity interfaces.

## Editor and diagnostics

The CodeMirror instance remains mounted when switching Input, Output, Problems, Test Results and History. Native diagnostics create underlines, gutter markers and hover messages. Problems include severity, line, column, original message and checker, and can be clicked to focus the code. Keyboard shortcuts include Ctrl+S, Ctrl+Enter, normal undo/redo/search, and Tab/Shift+Tab.

Live checking waits 750 ms after edits, configurable with `VITE_CODE_DIAGNOSTIC_DELAY_MS` (250–3000 ms). Outdated requests are aborted and their results discarded. The server cancels active checker processes after a disconnected validation response. Typing never runs the student's program. A busy/unavailable checker is reported as unavailable rather than as valid code.

| Language | Real checking technology | Verified in this environment | Actual student execution |
|---|---|---|---|
| Java | JDK compiler API, real `javac` diagnostics; annotation processing disabled | Local JDK 21.0.2; syntax/type errors, arbitrary public names and packages | Hosted OpenJDK 25; hello/stdin, errors, arbitrary public names/packages, both roles' Run/Tests passed |
| JavaScript | Node/V8 syntax parser; nonexecuting `node --check` for CommonJS and ES modules | Local Node 22.21.0; valid/invalid CommonJS and module syntax | Hosted Node.js 24; hello/stdin, errors, CommonJS and ES modules, both roles' Run/Tests passed |
| Python | Configured interpreter running `ast.parse`, never `exec`/imports from the student's source | Local syntax/indentation checks; standalone checks used Python 3.14.0 | Hosted Python 3.14; hello/stdin, errors, timeout, isolation checks and both roles' Run/Tests passed |
| Dart | Installed SDK parser and machine-format analyzer | Local Dart SDK 3.8.0; syntax/type errors, SDK imports and warnings | Hosted Dart 3.13; hello/stdin, errors, both roles' Run/Tests and optional final evaluation passed |

Java public class/package names are obtained from the JDK syntax tree, not guessed from regular expressions. Diagnostic positions account for UTF-16 editor offsets. Python positions are converted to UTF-16; Java positions preserve tabs rather than using expanded terminal columns.

Dart full analysis is limited to the single submitted file and direct `dart:` SDK imports. Non-SDK/file/package imports and complex interpolated strings receive genuine SDK syntax checking with an explicit notice that full type analysis is unavailable. User-controlled paths are never resolved by the analyzer. No Dart code is interpreted as JavaScript.

Trusted static checker helpers run in separate temporary workspaces with source limits, bounded concurrency, timeouts, output caps, no inherited application secrets and cleanup. These helpers only parse/compile; they are **not** a sandbox for executing student programs. Heavy model startup or machine resource pressure can temporarily exhaust checker timeouts; code/drafts are preserved and the UI reports the condition.

## Drafts and official submission

- Drafts are private to the authenticated student/activity and saved to PostgreSQL. A user/activity-scoped browser backup supports recovery when offline or the server is unavailable. Storage failures are displayed truthfully.
- Saves are serialized and use revision comparison plus the official submitted version. Another tab or an older request cannot overwrite a newer server draft. An unsent browser copy conflicting with the server copy is offered for explicit recovery.
- Initial restoration completes before source editing is enabled, avoiding a late restoration overwriting newly typed code. Changing tool panels preserves source, stdin and diagnostics.
- Save Draft, Run Code and Run Tests never submit the activity. The existing Submit Activity action saves the exact source snapshot. Late draft writes cannot alter the new official version. Locked resubmissions remain locked.
- Teachers may allow diagnostic errors for partial credit (default) or require errors to be corrected. The backend enforces that policy. Sample-output matching is not required unless the teacher explicitly configures passing tests as a submission requirement.
- Older unsupported-language activities and historical source records are preserved. New programming activities are restricted to Java, JavaScript, Python and Dart.

## Teacher settings, tests and grades

The existing Create Activity form includes sample input/output, expected output, explicit strict or trailing-whitespace normalization, optional student practice targets, public/hidden test cases, bounded CPU/memory limits, partial-credit policy and optional technical points. Existing activities have **Programming settings and test cases** in the class manager.

OnlineCompiler enforces a **fixed 512 MB memory cap and 16 processes**, not the old configurable Judge0 memory choices. These effective limits appear in the workspace/settings/results and saved test evidence. The configured 1–5 second limit is interpreted as provider wall time with its startup allowances. Existing requested memory settings are preserved as historical configuration, not advertised as enforced. The compatible API can report compilation failures as runtime NZEC with native compiler text; original messages/statuses remain visible, and unavailable exit codes remain unavailable. Local live checkers and hosted runtimes have different versions, listed above.

Students receive only public test cases; hidden names, inputs and expected outputs are excluded from their workspace responses. Student practice Run Tests uses only public cases. The assigned teacher's Run Tests uses configured public and hidden cases and displays authorized case details. Both roles have an execution-status refresh control; student refresh preserves the source, input and draft revisions. If configured and verified, final submission evaluation runs the teacher's configured cases, including hidden cases. Student-visible history removes hidden inputs/outputs and native output from hidden cases. The class teacher can inspect full records for that class/student/submitted version.

Actual stdout, stderr, compilation messages, native status, elapsed time, memory when provided, exit code and truncation are separated. Expected output never replaces actual output. Comparison uses only the teacher-selected normalization. Earlier-code results are labeled when the editor or stdin has changed.

An optional technical suggestion is calculated only when the teacher defines technical points. Results appear alongside the existing rubric review. **No execution result automatically publishes a grade or overwrites the teacher-approved score.** Existing AI-assisted rubric controls, grading overrides, reports and exports remain authoritative. No AI error-rewriting feature was introduced.

## Database changes

Idempotent schema initialization adds three small extensions to existing records:

| Table | Purpose |
|---|---|
| `activity_code_settings` | Teacher-owned settings/test cases linked to the existing activity. Keeping these outside `activities.*` prevents hidden-test leakage through legacy activity queries. |
| `code_drafts` | Private source/stdin/practice-target draft, revision, base submitted version and timestamp. |
| `code_runs` | Language, exact source/SHA-256, run/test/submission purpose, result, timestamp and optional existing submission/version reference. |

Practice history retains the latest 20 records per student/activity. Submission-version records are kept with their existing submission. Results use PostgreSQL `JSON` so authentic output containing control characters can be retained; the idempotent migration converts only the new `code_runs.result` column from an earlier `JSONB` definition if present. Text source/input fields reject NUL characters explicitly rather than silently altering source.

Activity creation and its code settings save in one SQL statement. Native validation and optional provider evaluation happen before acquiring the final submission's database locks. The transaction rechecks enrollment, attempts and the teacher's current configuration; changed settings reject the stale evaluation instead of saving it. Final submission and its code snapshot/evaluation reference then save together in the existing transaction. Run history also captures the actual stdin sent. No existing student, subject, enrollment, grade or historical submission was deleted or restructured. No packages or SDKs were installed.

## Execution configuration and renewal

The current managed connection and evidence are configured. [The setup guide](managed-code-sandbox.md) records the actual provider, environment variable names, verification and renewal. The following describes requirements for another deployment or a future provider change.

1. Provision and review a dedicated, maintained Judge0-compatible execution service with an isolation boundary appropriate for hostile programs. Ordinary subprocesses or an ordinary privileged Docker container are not substitutes. Keep application/database credentials and host mounts out of the workers.
2. Verify network denial, isolated temporary filesystems/cleanup, CPU/wall/memory limits, process/thread limits and output/file caps on the actual deployment. API request limits alone do not prove enforcement.
3. Verify all four real language runtimes using valid programs, stdin, native compile/syntax failures, runtime exceptions, infinite loops and memory/output exhaustion. Java must handle public classes other than Main and package-qualified entry points. A stock provider fixed to Main.java/Main may need an operator-configured runner; the adapter does not rewrite the student's source to hide this limitation.
4. Complete a deployment approval record based on that evidence. [The example](../backend/code-sandbox-approval.example.json) has every control disabled intentionally. It is an operator review record, not an automatically generated security certificate. Do not mark unverified controls as verified.
5. Configure these server-only environment values, restart the backend and verify availability per activity:

```env
CODE_EXECUTION_API_URL=https://your-dedicated-judge0.example
CODE_EXECUTION_APPROVAL_FILE=C:/path/to/operator-owned/verified-sandbox.json
# Optional provider credential; never expose this through a frontend variable:
# CODE_EXECUTION_API_KEY=...
# CODE_EXECUTION_API_KEY_HEADER=X-Auth-Token
# RapidAPI endpoints additionally need their API host and X-RapidAPI-Key:
# CODE_EXECUTION_API_HOST=your-api-host-from-the-dashboard
```

The approval must match the exact configured API URL, identify the reviewer and verification/expiry timestamps, and record evidence for required controls and tested languages. Java additionally requires `javaPublicClassNames: true`. Missing, invalid, expired or incomplete approval keeps the relevant runtime disabled. No unrestricted local-execution fallback is used. The current 30-day local record identifies which checks were observed live and which architecture/resource controls are provider-attested. Renew it after reviewing current provider behavior; do not fabricate evidence.

The ordinary Judge0 profile sends explicit network denial and resource fields. The OnlineCompiler profile omits fields its compatible API rejects or ignores, relying on the provider's documented and displayed fixed sandbox constraints. Both send original source once. Teacher settings are validated on the backend; student limit fields are ignored. Jobs have a bounded global queue and shared per-account concurrency/request quotas across Run Code, Run Tests and final submission evaluation. Responses have size/time limits; credentials are not included in student-visible provider errors and redirects are disallowed. A failure preserves code and shows an honest status.

Optional static checker paths are `CODE_JAVA_EXECUTABLE`, `CODE_JAVAC_EXECUTABLE`, `CODE_PYTHON_EXECUTABLE` and `CODE_DART_EXECUTABLE`. Use real executables, not shell wrappers. Python also respects the existing `PYTHON_EXECUTABLE`. Installed SDKs are discovered where available, including Flutter's bundled `dart.exe`.

Real output, native error reporting, stdin execution, timeout enforcement, network denial, fresh workspaces and actual test evaluation have now been observed with authored fixtures. Fixed memory/process caps and gVisor/host isolation are provider-attested, not independent infrastructure audit results. No existing student work was sent during verification. Run Tests requires configured cases; students need at least one public case. Browser visual/cursor interaction remains a manual check.
